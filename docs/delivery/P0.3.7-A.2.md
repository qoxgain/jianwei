## SQLite备份安全性与锁顺序

旧顺序构成环：Backup持commit_gate等待SQLite写者；Writer持EXCLUSIVE等待commit_gate。固定基线实际复现：DELETE busy_timeout=200ms，等待超过1秒后两者仍未完成；WAL对照完成且独立连接读取提交行。

新顺序：**短时闸门健康检查 → 释放闸门 → 独立只读SQLite复制/完整性/外键/SHA/fsync → 释放所有SQLite资源 → 短时闸门复查 → 原子无覆盖发布与published回执**。耗时阶段不持全局提交闸门；文件源也不经可能在EXCLUSIVE下等待的受管PRAGMA初始化。详见上面的Mermaid时序图。

统一配置 `sqlite.backup`：timeout_seconds=10、pages_per_step=64、retry_seconds=.01；旧配置未显式提供该字段时，历史配置快照不增加默认块。等待发布边界也分片检查取消/截止时间。Database.close取消本实例在途备份。

开始前故障拒绝；复制首/末页期间由另一实例真实持久化故障，停止并保留invalidated回执/partial；复制后再复核健康，故障不能夹在检查和有效发布之间。先完成published、后记录故障，则历史成果保持完成顺序，不能据此解除原库隔离或重开已消费测试。没有恢复/清标记接口。

备份只发布到新目标；同名并发只有一个成功，既有文件/符号链接不覆盖。失败留在独立partial和failed/timeout/cancelled/invalidated回执，不作为有效目标发布。内存库仍可备份。原生backup目标的组合式能力边界及row_factory防线未放开。

截止时间是对正常本地SQLite与文件系统的协作式有界处理；可信progress观察者须短时且不执行数据库事务。任意阻塞内核I/O、恶意回调和外部复制/恢复不属于本轮保证。历史 `database disk image is malformed` 根因仍未确认。

## 缓存与租约关键变化

优化缓存的授权不再来自可写metadata文件名或同目录摘要。Rolldown在写盘前对实际生成输出给出进程内摘要/内容，HTTP逐次复核磁盘当前文件，发送已证明内存副本避免二次读盘竞争。仅需要原生ES模块与调试map的GET/HEAD及正常v/t/import查询；raw/url、未知查询、缓存Range拒绝。SourceMap响应头保留调试关联，显式受审清单采用原子写入与真实HMR刷新。

源码/受审清单/锁文件/安装依赖/打包器/进程内存为可信；攻击者只能修改普通缓存或其metadata，不能因此自行获得发布授权。任意本机代码执行或管理员改可信根不在范围内。开发服务默认loopback，并应使用不挂载正式封存、工业特征/权重、生产数据库的隔离工作区；上传不得写优化缓存。

租约绑定执行者，父授权失效后复制的ContextVar不能授权子任务。run_sync显式授给特定工作线程；原生asyncio取消可先结束父任务，但已开始的受控工作仍由真实锁资源引用保护，工作finally结束才释放。异步等待继续不占共享AnyIO令牌，不以扩线程池解决。普通跨任务/未受控offload不自动继承授权。
