# SQLite 异常调查与可靠性验证

原探索事件报告的失败库 SHA 为 9ac5ceb18424cb1fd53800e936460213789c4a5c74076df0d612d8ee931008c2，593920 字节。当前工作区及可访问临时目录没有找到匹配原库；只取得探索分支的错误与 SHA 记录。因此原始损坏不能复现，根因仍为 **not_established**，不能认定已修复原故障，也不能据此推断正式库受损。原数据库、研究记录、特征和权重没有改写。

## 已实现的保护

- 可选 system.yaml `sqlite` 策略：日志模式、FULL/EXTRA 同步、busy timeout、启动完整性检查、最低可用空间。默认仍为 DELETE/FULL；WAL 必须显式配置，见 examples/sqlite-policy.yaml，不将 WAL 宣称为损坏修复。
- 迁移前 quick_check/外键检查；进程内及 SQLite 文件迁移锁，失败不自动修复/恢复。跨 fork 连接池拒绝父进程连接并重连；生产建议 spawn，不能将连接 PID 检查当作任意多线程 fork 安全保证。
- 写语句与 ORM 提交前低空间检查；识别 CORRUPT/NOTADB/IOERR/FULL 后记录故障，暂停任务工作线程和新事务；API 返回明确不可用，避免失败被解释为已提交或原轮询 KeyError。
- 在线 SQLite backup 只写新文件并验证 integrity_check，禁止覆盖已有备份；无自动原地恢复。恢复前须人工核对来源分区及封存消费记录，不能通过旧备份使已看过的测试重新封存。
- scripts/inspect_sqlite_copy.py 将 DB/WAL/SHM/journal 原字节和 SHA 保存到全新 evidence/raw，再仅检查 working 副本，绝不让 SQLite 打开原文件。文件复制不是原子在线备份，取证前应停止写者；并发变化时明确不确认一致性，不报告原库已损坏。

## 实际验证与限制

12 项数据库/迁移/API 基础检查通过，扩大到异步任务、取消、缓存及迁移相关回归共84 passed；最终工程全量 **542 passed、0 skipped**，前端 **93 passed**、生产构建与参考 **29 passed**。故障注入使用临时库：DELETE 与 WAL 下线程/多进程写入、未提交取消、进程直接退出、提交保留/未提交回滚、fork 后重新建连接、备份重开与记录一致、损坏文件拒绝迁移、副本保留、模拟低空间拒绝写入。测试没有填满共享磁盘，低空间是明确的注入用例。

本机文件系统为 overlayfs，不能外推到客户 NFS/SMB、断电、硬件故障或任意驱动。SQLite 文件锁/WAL 仍依赖受支持的本地文件系统；没有观察到原事故同型的自然损坏。启动完整性检查是当时状态，不保证未来 I/O 永不失败。后续需在原故障副本/运行日志、磁盘及挂载信息可得后继续取证。

工程阶段完成后方进入算法优化。CI 只上传数值 JSON 证据，新增数值特征/权重/数据库文件被忽略，原视频及衍生画面不作为本轮公开制品。

选择性迁入探索分支已验证的 poll_import/HTTP 结构检查（未合并整个分支），并补非JSON响应证据；5项轮询回归通过，失败保存本地原始响应而不再索引不存在的 status。工程保护最后一轮数据库/接入/时序任务回归26项通过。原事故是否由文件系统、多进程或其他原因引起仍未确认。
