# A2 / R02 故障与提交顺序

固定基线反例已复现：临时库Core INSERT后记录SQLITE_IOERR，正常退出session仍提交1行。这是故障闸门范围的确定反例，不能解释历史真实损坏的根因。

已改为DBAPI实际commit门控，覆盖Session/Core/ORM flush、Engine事务、受管理raw_connection、连接上下文以及直接SQL COMMIT/END/RELEASE。故障检测和实际提交使用同一同机跨进程锁：故障先记录则提交拒绝并回滚；实际提交先进入锁则先完成，故障随后生效，不逆转已提交事实。普通SQL执行不长时间持提交锁，避免等待SQLite写锁的事务阻塞原写者提交；DDL也显式纳入事务。SQLite authorizer在prepare时核查写入空间，覆盖注释及WITH前缀，不只依赖SQL首词。关闭prepared statement缓存以避免跳过authorizer；隐式提交executescript和附加外库在受管理连接中拒绝。

首次严重故障在DB旁新增只写一次的 `.fault.json`，文件存在但不完整也按隔离处理。其他受管理实例/进程可见，重启不自动清除，故障后新事务拒绝，在途事务不能提交。回滚和关闭仍允许；不依赖损坏的DB写终态来宣布任务已完成。旧备份覆盖DB本身不清除侧文件隔离，因此不会自动重新开放已消费的研究数据。没有提供自动恢复或解除隔离接口。

专项测试使用真实临时SQLite连接、线程屏障和spawn进程，验证Core/ORM/Engine/raw/context/直接SQL、CTE低空间、故障先于提交、提交先于故障、跨实例/进程、重启与旧备份恢复。已有DELETE/WAL并发、异常退出、取消回滚、迁移及研究消费测试保留。最终结果见总报告。

边界：保证限于经Database创建的连接、同一规范化DB路径和可靠本地flock/文件系统。外部sqlite3进程、管理员删除隔离标记或复制数据库到新身份、硬链接替代、跨节点、不可靠NFS/SMB不受此门控约束。若文件系统连新增隔离标记与fsync都无法完成，仅本进程内存故障可可靠锁定，不能声称跨进程耐故障持久化；需停止所有写者并取证。多线程fork不作为安全进程启动方式，使用spawn。没有声称覆盖断电/磁盘硬件故障，也没有确认原database disk image is malformed根因。

恢复必须离线保留原DB及WAL/SHM/journal和隔离证据，核对独立保存的消费水位/审计后再人工制定迁移；不能删标记或恢复旧备份把看过的数据重新封存。本轮未触碰任何原始失败库/正式研究记录。

原生提交路径复核：CPython的isolation_level/autocommit赋值也可能在C层直接提交，现已使用同一提交锁和故障检查保护；直接BOM/分号/注释前缀COMMIT也纳入识别。拒绝受管理连接的blob直写路径。新增两项原生setter反例，故障与既有可靠性专项合计22项通过。
